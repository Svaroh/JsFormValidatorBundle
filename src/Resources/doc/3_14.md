### 3.14 Localized numbers

`NumberType`, `IntegerType`, `MoneyType` and `PercentType` render their value
with the conventions of the current locale. With the `it` locale, for example,
decimals are separated by a comma and thousands by a dot, so the field holds
`1.234,5` where the model holds `1234.5`.

Constraints are declared against the model value, so the bundle reverses the
formatting before it validates, exactly like the Symfony view transformers do
on the server. Nothing has to be configured: the factory exports the decimal
separator, the grouping separator, the grouping flag, the scale and the
rounding mode of every localized field, and the JavaScript transformers read
the value with those rules.

```php
$builder->add('discount', PercentType::class, [
    'scale' => 2,
    'constraints' => [
        new Assert\Range(min: 0, max: 1),
    ],
]);
```

Typing `12,5` in an `it` form is validated as `0.125`, the same value the form
would submit.

A few details are worth knowing:

- The rules come from the transformer of each field, so options that change the
  formatting are honoured. An `IntegerType` without `grouping`, for instance, is
  rendered with the `en` locale by Symfony, and it is read back the same way.
- Everything the formatter of the locale writes is read back: the minus sign of
  `sv` and `fi`, which is U+2212 rather than a hyphen; the digits of `ar` and
  `bn`, and the ones of `ccp`, which lie outside the basic multilingual plane;
  the exponent of `sv`, which is `×10^`; and the grouping of `hi` and its
  neighbours, which takes the leading digits two at a time.
- The submitted value is trimmed first, exactly as the `trim` option of the
  field makes Symfony trim it, so a field declared with `'trim' => false` keeps
  the leading space that the formatter refuses.
- A value that cannot be reversed at all — letters, or a separator that does not
  belong to the locale — is reported with the `invalid_message` of the field,
  and its constraints are skipped. This mirrors what Symfony does with a failed
  transformation.
- The locale data is read on the server, which needs the `intl` extension for
  these field types. Without a usable formatter the JavaScript falls back to a
  dot for decimals and a comma for thousands.

## Where the browser is stricter than the server

Three inputs are refused here that Symfony would have accepted. They are
refused on purpose: in each of them the server reads a value that has nothing
to do with what was typed, so an error is the honest answer.

- Digits of a script the locale does not use, pasted into a form of another
  locale. The formatter reads `٠١٢` as `12` under `en`; the browser does not.
  Digits the locale itself writes are always read.
- `NaN` in a `PercentType`. `PercentToLocalizedStringTransformer` carries no
  check for it, unlike its number counterpart, and reads it as `0`.
- A `PercentType` value that reaches `PHP_INT_MAX`, which the same transformer
  reads as an overflowed integer.
